## Design choice: a thin router

Nebi remains a small set of cross-cutting workflow skills (seven since 2026-09-23, when `nebi-hillclimb` gave the measure-first improvement loop its own trigger) plus one harness core per client. Since 2026-10-03 one Claude Code–only skill sits beside them: `nebi-mod-verify`, our own paint check for the nebi mods. It is not a mega-skill or a bundled agent framework.

- The core carries only standing preferences, harness bindings, and broad proof rules.
- Each skill loads one method only when the task calls for it.
- Third-party skills install where they are used: one project locally, several projects globally, always for both clients.
- Skills pass compact artifacts to one another instead of loading an entire pipeline in advance.
- Third-party packs add context, trigger competition, executable surface, and update risk, so each one is reviewed and pinned. A pack the user names is installed from its real upstream and recorded in `upstreams.json`; rewriting it in Nebi's words or deferring it is a deviation the user hears about with its reason.

This matches the official Agent Skills guidance on scoped skills and progressive disclosure while preserving Nebi's direct-instruction override.

## Maintenance loop

1. Read the request, current masters, and relevant failure-log entries. Start with targeted local reads.
2. Start with `node claude-home/nebi/upstreams.mjs --docs` for the official pages that changed or gained posts since review. Run discovery read-only using primary documents and source metadata. Inspect an unfamiliar executable before running it; a package-runner or help command may install or execute code. Check current help for already reviewed installed CLIs when syntax matters.
3. Record what changed upstream, what real failure it addresses, and whether an existing rule already covers it. Leave speculative features out.
4. Update the smallest relevant master. Keep shared skills active-harness-neutral and model-free. If bindings change, update both harness cores and dates together.
5. Validate proportionally:
   - Body-only prose: frontmatter/structure, readback, relevant diff, and formatting smoke.
   - Description change: the affected skill's focused must-fire and near-miss suite.
   - Executable change: syntax checks plus the smallest focused fixture or dry run that exercises the affected path.
   - Full cross-model or baseline evals: only broad trigger changes, unresolved regressions, releases, or explicit requests.
6. Update this source record and change log. Do not silently install or update third-party material.
7. Deploy only when requested. Use `node deploy.mjs --check` first; use `--home` for isolated staging. Preflight required masters and nested JSON merge shapes before writes, then verify copied/seeded files and generated JSON. Later I/O failures can still leave partial deployment.
8. Run `node ~/.claude/nebi/skill-usage.mjs --days 30` and compare with the newest usage ledger in `benchmarks/`, following its next-review section. Measure the active client's skill listing/context behavior and focused trigger recall. Do not enforce a universal skill count; scope each pack by where it is used, and check `node claude-home/nebi/upstreams.mjs` for packs that are behind, edited, unregistered or visible to one client only.
9. If a prose rule repeatedly fails, make it deterministic where the harness supports that safely, or delete it.

## Deploy contract

`node deploy.mjs [backup-suffix] [--home DIRECTORY] [--check]` is the supported deployment path; `deploy.sh` and `deploy.ps1` are thin wrappers around it.

- Preflight: every required master and the JSON merge targets (`~/.claude/settings.json`, `~/.codex/hooks.json`) are validated before the first write; a failure leaves every target untouched.
- Claude Code: copies its masters, native agents, shared hooks and context helper; seeds only the failure log; merges only Nebi-owned statusLine/outputStyle/hook entries, one `claudeMdExcludes` entry for `~/AGENTS.md`, and a default `skillListingBudgetFraction` (0.02, only when unset). The upstream register and its checker deploy to both clients. Authored project/task checkpoints live outside the deployment manifest.
- Codex: copies `AGENTS.md` to the lowercase `~/.codex/` (backing up an existing one), this file to `~/.codex/nebi/`, and the seven common skills with `triggers.md` and `evals.json` to `~/.agents/skills/`; seeds never-overwritten state, and merges only Nebi hook entries into `~/.codex/hooks.json` (new definitions need Codex's trust step). No Codex settings or rules are changed.
- Backups: `settings.json`, `hooks.json`, and an existing `~/.codex/AGENTS.md` are backed up to `<file>.<suffix>` once; an existing backup is never overwritten, so the first run's copy stays the pristine pre-Nebi state.
- Post-write verification: every copied or seeded file is byte-compared against its master; any mismatch fails the run loudly.
- Report-only checks: measured skill-listing sizes, bindings-date parity, and section-heading parity across both harness cores.
