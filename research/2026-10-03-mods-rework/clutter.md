## Summary

Most of the clutter goes away with settings, env vars and small edits to Nebi's own files. Three items need mod code, and one needs a careful mod:

1. **The repeated "Stop hook feedback: N background tasks still running" is a bug in `verify-before-stop.mjs`.** The artifact comment watcher is a `monitor_ws` task the engine registers with `ambient:true, persistent:true, timeout_ms:0`. The Stop payload keeps it as `{type:"monitor", status:"running"}` and drops the `ambient` flag. The hook counts it as unfinished work on every stop for the rest of the session. It also hides the hook's other two checks (early stop, done without proof), because `running>0` returns early and the early-stop test needs `tasks.length===0`. Recent transcripts contain 1,414 such lines across 34 sessions in 3 days, and every one of those sessions published artifacts.
2. **"▲ nebi-constellation: 3 need you" comes from `$.ui.status`.** The engine draws every plugin status as a pinned notice: the `⚠` glyph (U+26A0, which shows as ▲ in his font) plus `<plugin>: <text>`, colored `warning`. A plugin can change neither the glyph nor the color. The fix is to stop using `$.ui.status` and put the count somewhere quiet: a `SessionMode` label or a `PromptHint` tail.
3. **The NEED YOU card's numbered answers are built by nebi-beacon itself.** A `$.model.fork` asks for up to 3 options (`parts.ts` ASK_MAX.options), and the band draws them as Buttons with hotkeys 1-3 plus a 0 for dismiss. The output style adds to it: it tells the model to re-ask open questions "with the options and your recommendation".
4. **"(shift+tab to cycle)" has no setting.** A `PromptHint` hook that rewrites `hint` drops it and keeps the mode visible: the engine strips the mode label out of `hint` and redraws the colored mode pill itself in front of a rewritten hint. The catch is that a rewritten `hint` throws away every other mod's `tail`, so one mod must own the footer.

## Details by item

### 1. Status line
- `model.display_name` reaches the statusline script already ending in " (1M context)": `Fo(Pe)` → `nv()` adds the suffix when the model id ends in `[1m]` and the model supports it (bin@15232563, bin@21591065). His `settings.json` has `"model": "opus[1m]"`.
- statusline.mjs:30 adds `" (1M)"` again to the ctx segment when `context_window_size >= 1000000`.
- Lever: two-line edit in `claude-home/nebi/statusline.mjs`, then `deploy.mjs`. Keep `ctx 45%`. Model id and window stay unchanged.

### 2. "(shift+tab to cycle)" and the PromptHint mechanics
- Footer composition (bin@42175952, function `qBe`/footer row): `rs = vx({mode, children: Gn && _s && " (shift+tab to cycle)"})`. `Gn = !$Jo(mode)` (mode is not default). `_s = ur<2 && width checks`, where `ur` counts the mode plus a background-task indicator. No settings key, env var or "seen once" flag gates it in this path. (The other footer `Ise` has a `cycled` memo, `DYt.of(host).cycled`, but that isn't the path drawn here.)
- PromptHint reading (bin@42178604 `Wse`): the `hint` string is the drawn footer row with the mode label (`"<mode> on"`) cut out and a leading " · " trimmed. The prop therefore starts with "(shift+tab to cycle) · …", or just holds the rest of the line.
- PromptHint drawing (EK, same offset): when a hook's drawing differs (hidden flag `Ne`), the engine sets the original row to `display:"none"` and draws `[ vx/BM({mode}), " · " ] + PromptHintSite(rewritten hint)`. The pill is drawn **without** children, so the cycle hint is gone and the colored mode stays.
- Contract impact: CONTRACT.md:10 tells mods to append to `tail` only. A `hint` rewrite drops tails (types:9564-9565: "A rewritten `hint` replaces the line, `tail` with it"). The footer needs one owner: it folds `e.props.tail` into the rewritten hint, and model-lock's 🔒 either keeps its tail (if the owner runs closest to the engine) or moves into the owner. Plugin hook order is unconfirmed, so folding is safer.
- Verify before building: a 5-line mod that does `$.ui.log(JSON.stringify(e.props), {to:'debug'})` on PromptHint, to see the exact `hint` text in bypass mode.

### 3. NEED YOU card
- Data path: `turn.complete` → `parseStatus(e.answer)` → `asksPerson` → `frameAsk` → `$.model.fork({prompt: askPrompt(text)})` → `parseAsk` → `ask` atom `{kind:'card', card:{what, why, reply, options}}` (register.tsx:300-335, 183-204; parts.ts:201-256).
- Drawing (register.tsx:346-481): badge `❓ NEED YOU` (black on #ffd23f); headline `card.what` bold and wrapped; `why · reply with “…”` dim; `options.map` → `<Button hotkey={i+1}>` plus `<Button hotkey="0" label="dismiss">`. While the fork runs, a "dots" Raster animates.
- Smallest change that meets "short, clear needs-you, no answer options": keep the badge plus a one-line `what`, delete the Buttons, the `reply with` text and (optionally) the `why` line. Even smaller: skip the fork and use `b.text` (the status line after "❓ Need you —"), which the output style already makes self-contained. The speak and push in `frameAsk` can move to `turn.complete`.

### 4. Constellation ▲
- `$.ui.status(text)` → engine host `status(plugin, text)` → `removeNotification('plugin-status-<plugin>')` then `addNotification({key, kind:'event', text:'<plugin>: <text>', priority:'low', pinned:true})` (bin@41617596, bin@24575679).
- Pinned notices are drawn by `P1`/`tre`: `<Text color={notice.color ?? 'warning'}>{KS} {text}</Text>`, with `KS = "⚠"` (bin@42118931, bin@42119977, bin@12963846). A plugin has no way to pass `color` or drop the glyph or the name prefix.
- Toasts (`$.ui.toast`, register.tsx:175 "⌁ project needs you: …") are separate one-off notifications (`plugin-toast-…`, priority immediate, bin@41617596). They are lighter but still say "nebi-constellation: …".
- Quiet alternatives: **SessionMode** (bin@42140407 `BF`: `modes.join(" & ")`, dim, right side of the footer, raised on terminal and desktop), or the footer owner's PromptHint text. A loud alternative is a badge in the shared band, but the band belongs to the beacon (CONTRACT.md:9-11).

### 6. Stop hook (the clearest bug)
- Payload shape (bin@13894173): `background_tasks: [{id, type, status, description, command?, agent_type?, server?, tool?, name?}]`, documented as "In-flight background work (running/pending + backgrounded)".
- Builder `Gqt` (bin@22584829) includes every task where `hg(task)` holds: running or pending, and not `isBackgrounded===false`. `monitor_ws` has no `isBackgrounded` field, so it is always included. Its `type` becomes `"monitor"` (bin@18298626), and the `ambient` flag is dropped (`case"monitor_ws": break`). The internal `background_tasks_changed` event and `running_background_tasks` metadata do carry `ambient:true` (bin@29721137), but the hook never sees them.
- Artifact watcher (bin@27706799 and bin@27642454): `timeout_ms:0, persistent:true, quietLifecycle:true, ambient:true`, with description `live updates for artifact <url> (<task>)` or `presence on artifact <url>`. It is armed for publish/attach/watch/resume (`KEo=["publish","attach","watch","resume","session_resume","mcp_write"]`, bin@27407995).
- Hook effects today (verify-before-stop.mjs): `countRunning` (51-55) counts the watcher, so it emits "N background tasks still running …" (86-94) on every stop after the first publish. Because that branch returns, the §3 early-stop check (105, which also needs `tasks.length === 0`) and the §6 proof check (114-142) never run while a watcher is armed.
- Minimal fix (about 3 lines): `const work = (tasks ?? []).filter(t => !(t?.type === 'monitor' && /^(live updates for|presence on) artifact /.test(String(t.description ?? ''))));`. Use `countRunning(work)` and `work.length === 0` where `tasks` is used today, keeping `tasks === null` to mean unknown. Wider variant: drop every `type === 'monitor'`.
- Evidence it is the main noise: `grep` over the 34 transcripts touched in the last 3 days found 1,414 "N background task(s) still running" lines. Every session with them also had Artifact tool calls, and several had no Monitor or background Bash at all (per-session counts in scratchpad).

### 11-12. Rewriting ToolResult and ToolUse rows
- `ui.render` semantics (types:3754-3765): return `next(e)`, wrap it, draw your own, or rewrite `props`. `next(e)` returns `{type:'engine', ref}` (types:9033-9042): an opaque handle. **A hook can't edit the engine's tree** (for example, to delete one child line). It can only rewrite props or replace the whole drawing.
- ToolResult rewrite of `output` is checked against the tool's output schema (types:9272-9274). Drawing your own tree is simpler for Write. ToolUse (bin@40692838) wraps `Xu`, the whole row including progress messages, so replacing it collapses the Workflow progress.
- Neither ToolResult nor ToolUse has an `isExpanded` prop. UserMessage and ToolGroup do (types:9157-9166, 9333-9340). That is the ctrl+o risk.
